本轮把应用场景聚焦为：

4.1 明确三类具体痛点

学生侧：
学生做错题后，往往只得到答案或一般性解释，却不清楚自己缺少哪项基础、应该先补什么，以及有限时间内怎样安排下一步学习。

教师侧：
教师面对多名学生的作答，单看总分难以识别不同困难；从发现问题到组织讲评、分层练习和复测，需要反复整理资料与匹配对象。

师生衔接：
资料、视频、练习、辅导和教师任务分散，学习建议难以落到具体活动，任务完成后也缺少与原问题对应的后续反馈。

以上内容要结合当前产品实际能力，用清楚的工作场景表达，不写成泛泛的“传统教育存在不足”。

4.2 每个痛点对应具体功能与产出

学生不知道下一步学什么：
对应 K-TRACE 状态估计、PATH-G 约束规划，以及能直接打开的题目、资料、视频片段和复习任务。

学生得到解释却未必理解：
对应 DIA-GUIDE 的上下文辅导、不同教学策略、交互实验、理解检查和后续反馈。

教师难以区分同分学生的具体困难：
对应 CLASS-LOOP 的证据与错因分层，以及能够查看原始作答的学情入口。

教师分析之后仍要手工组织教学：
对应 DIA-TEACH 的目标与班级证据结合、教学草稿、题目匹配和确认发布。

任务发布后难以跟踪：
对应任务标识、学习事件、理解检查、教师反馈和下一轮安排。

文档、README 和视频使用同一套“问题—方法—操作—结果”关系，不分别写出三套不同故事。

4.3 实际验证平台不是只能播放预设样例

在隔离测试环境中检查一条新建教学单元的流程：

教师新建或导入一小份自编教学资料；
配置少量知识点与关联题目；
资料进入检索；
学生在该单元完成练习和辅导；
系统生成对应任务；
教师查看结果并发布后续安排；
学生完成后结果回流。

使用现有功能完成，发现必须依赖固定课程编号、硬编码知识点或预设学生才能运行的地方，再做针对性修复。

这项验证不要求新增一整门大型课程，也不要求为了填充内容大量调用 API。它用于证明平台具备实际内容接入与教学组织能力。

4.4 实用价值的表达方式

优先用能观察到的结果说明价值：

定位到了哪个具体困难；
推荐打开了哪段资料或哪组题；
生成了什么可编辑教学产物；
教师怎样确认并发布；
学生完成后出现了哪些新证据；
后续计划如何变化。

引用已有教育研究时，使用真实来源并在正文对应处标注。

没有实际开展的课堂试点、用户访谈、教学合作、提分实验或节省时间统计，不写成既成事实。

课程任务验证与真实教学效果研究分别表达。集中说明数据来源即可，正文保持自然，不反复自我辩解。

6.1 框架内容

第一部分：师生任务与输入

学生：
课程学习、题目作答、问题与附件、学习目标。

教师：
教学目标、课程资料、班级任务、学情问题。

第二部分：共享课程与证据基础

课程知识图谱；
讲义、视频、题库；
作答与理解检查；
任务、学习事件与历史；
课程权限和版本化内容。

第三部分：核心方法

K-TRACE：
将作答、提示、时间和有效证据转为知识状态。

PATH-G：
结合状态、先修关系、目标与时间预算，形成可执行学习路径。

DIA-GUIDE：
围绕学生困难组织诊断、教学策略、模型解释、学习动作和理解检查。

CLASS-LOOP：
依据班级学习特征和错因形成教学关注群组及匹配任务。

DIA-TEACH：
结合教师目标与授权班级证据，生成教学方案和任务草稿，经确认进入正式业务。

第四部分：AI 与工程支撑

课程和附件检索、来源定位；
DeepSeek 模型服务；
本地语音转写与文件解析；
结构化输出、对象校验和确定性评分；
数据持久化与学习事件反馈。

第五部分：实际产出与反馈

学生：
具体学习活动、个性化辅导、理解检查和复习安排。

教师：
教学草稿、分层任务、讲评与反馈。

实际执行后产生新证据，进入下一轮状态更新与教学安排。

6.2 图中的关系要准确

五项方法不是所有请求都必须依次经过的串行流水线。

区分：
数据流；
算法结果；
AI 辅导与生成；
教师确认后的业务写入；
学习反馈。

DeepSeek 提供解释与生成能力，不直接任意修改成绩、掌握度或已发布任务。

Whisper 是输入处理组件，不与五项核心教学方法并列成第六项核心算法。

Codex 属于开发过程工具，不要把它画成平台运行时必须在线依赖的教学服务。

技术栈可以放在简洁支撑区域，不用大量框架 Logo 抢占核心方法的位置。

6.3 图形设计

采用清楚的分区和有限层级，优先考虑师生双侧布局或双泳道结构。

学生青瓷、教师茶褐作为主色；共享证据与模型服务使用协调中性色和少量辅助色。

节点数量克制，标签简短，箭头方向明确，交叉尽量少。

让读者先看到主流程，再看到算法分工。不要把每个接口和数据库表塞入一张总图。

图中文字和连线保持可编辑。优先使用 SVG、TikZ 或其他可重复生成的矢量方式，不采用带有难以校对文字的整张生成图片作为正式框架图。

6.4 一套源文件，三处使用

文档：
在总体方案与方法介绍之间放置总图，并有正文解释。

README：
项目简介和作者信息之后，靠前展示总图，再给出功能与运行入口。

视频：
在背景和痛点介绍之后、界面演示之前展示，按讲解依次强调学生侧、教师侧和反馈关系。

三处可以调整比例和信息密度，但术语、方法名称、箭头含义与逻辑保持一致。

交付可编辑源，以及适用于 PDF、README 和1080p视频的导出文件。

检索消歧实验不能改写成通用问答准确率。

分组原型纯度不能直接等同于真实学生分类正确率。

方法和系统能力以工程证据、实际操作和明确的算法行为论证，不追求没有依据的“首次”“领先”或“显著提分”。

方法章节减少名称堆叠。每项方法都回答：
为什么需要它、怎样计算或组织、产生什么输出、用户如何感知。

涉及系统有效性的解释集中、自然，避免每段重复强调“不能证明什么”。

九、GitHub README 同步升级

README 开头调整为：

作品名称；
一句话定位；
学校、专业、作者；
简短的真实问题与解决方式；

主简介面向第一次看到项目的人，不以“第几轮做了什么”的开发日志作为第一段核心介绍。

版本演进放入更新记录或专门章节。

保留：
功能结构；
五项核心方法；
技术架构；
依赖和环境变量；
启动步骤；
教师与学生体验；
核心教学流程；
测试与复现；
资料来源和许可说明。

对当前本机运行方式如实说明。不要为强化实用价值临时宣称已经提供正式云端部署、校内试点或大规模并发能力。

总框架图在普通 GitHub 页面宽度下清晰可读，使用仓库内相对资源链接。

十一、视频画面：重做当前简陋的说明画板

用户提供的画面中存在以下问题：

左侧长期占用较宽区域；
主体只有少量句子；
中间大片空白；
信息焦点不明确；
文字、分隔线和背景缺少精细设计；
旁白内容主要被重复写在画面上；
整体像内部说明页，而非正式作品展示。

本轮重做所有同类封面、背景页、方法介绍页、过渡页和开发证据画板。

11.1 统一视觉语言

延续学脉的青瓷、茶褐、纸白和深墨色，形成一套独立的视频视觉系统。

重点建立：

明确标题；
合理字号；
整齐的图文网格；
实际产品画面；
核心图形；
克制的强调与转场；
足够但不过量的留白。

避免“左侧固定菜单＋右侧两句文字＋大片空白”重复贯穿视频。

说明画板不需要模拟一个不存在的应用侧边栏。

真实系统录屏则保留真正的左侧导航、顶部栏和完整工作区。这两类画面分别设计，不混淆。

11.2 各类画面

封面：
作品名称、清楚的定位、作者信息，配合精致的产品视觉或真实界面组合。

背景：
用学生困惑和教师任务表达具体问题。可以使用简洁流程、两端对照或少量真实界面，不堆大段教育口号。

总体框架：
使用本轮统一总图，根据旁白逐步强调相关区域。始终保留空间方向，不做无意义旋转或复杂飞入。

产品演示：
以真实应用操作为主，必要时进行克制的鼠标强调与局部结果标注。

开发过程：
突出实际 Prompt、代码差异、测试与最终效果。避免一屏放满难以阅读的长记录。

结尾：
一句明确的价值总结、作者信息和感谢语，不罗列一长串技术名词。

11.3 视频质量

继续使用真实连续录屏，不退回低频截图拼接。

应用保持100%页面缩放，文字可读，动画自然。

完整界面为主；关键细节可以短暂放大，但不长期裁掉导航或用局部画面冒充完整应用。

保留已有质量良好、与当前版本一致的素材；被修改的登录页、总图、作者信息及新画板重新制作。

十二、系统演示：以完整教学任务证明实用价值

使用一个稳定、清楚的主案例贯穿，不在每个镜头切换不同学生和知识主题。

建议保留已经跑通的“栈与队列学习—辅导—教师分层任务—反馈”案例，并增加足够停留时间展示关键结果。

主流程至少包含：

学生当前学习目标；
一次具体作答及错误；
知识状态与下一步学习安排；
图谱或视频片段定位；
AI 针对性辅导与资料引用；
交互实验或理解检查；
教师查看对应学习证据；
教师 AI 形成讲评或分层任务草稿；
教师确认发布；
学生完成对应任务；
教师查看新增结果并给出反馈。

每一步讲清“为什么做这一步、系统帮忙做了什么、结果在哪里”，而不是仅朗读按钮名称。

适当展示模型选择、附件或语音输入，但围绕教学任务使用，不把这些能力做成孤立的按钮巡览。

同时用少量镜头说明它能够扩展课程和接入新内容，避免给人只服务于一道栈题的印象。

保持操作与数据对应，复用同一课程、学生、知识点和任务标识。

真实 AI 片段优先使用已有合法保存、与当前版本一致的真实结果及录屏。重新录制需要生成新结果时，只进行少量必要调用。

不为重复拍摄反复消耗模型额度。

十三、讲稿与人声：按照真人参赛汇报重写

现有讲稿偏逐项说明界面与实现，本轮改为自然、清楚、有交流感的参赛汇报。

13.1 开场

在允许署名的版本中，开场以以下内容为基础：

“各位评委老师好，我是西安交通大学软件工程专业的刘嘉程。下面介绍我的参赛作品《学脉》，一套面向学生学习和教师教学的 AI 个性化智慧教育平台。”

随后直接进入具体问题，例如：

“学生做错一道题，往往知道了答案，却还不知道自己究竟哪里没学会；老师看到分数，也很难及时为每个学生安排不同的练习。学脉希望把这两端连接起来。”

依据最终时长精修措辞，不必机械照读示例。

13.2 中段

采用自然的操作讲解：

“先看学生端……”
“这里可以看到……”
“这一步之后，系统会……”
“再切换到教师端……”
“老师不需要重新整理这批数据……”
“下面看这项任务怎样回到学生手中……”

这些表达按语境使用，不要每段都重复同一句式。

减少“赋能、重塑、全方位、打造闭环”等空泛词语。

必要的技术名词保留，但先说明功能，再给出方法名称。

五项方法不必全部在旁白中逐字拼读英文缩写，可以使用“知识状态估计”“学习路径规划”“学生辅导”“动态分层”“教师教学编排”等中文表达，画面显示正式名称。

真实开发部分再具体解释意图、约束、修改与验证。

13.3 结尾

总结已经展示的价值，最后明确感谢评委，例如：

“以上是《学脉》的主要功能和开发过程。它把学生的具体困难转化为下一步学习，也让教师能够依据反馈继续调整教学。感谢各位评委老师的观看与指导。”

结尾画面同步显示作品和作者信息。

13.4 配音自然度

选择适合正式参赛汇报的自然普通话声音，语气平稳、有交流感，避免新闻播报腔、广告腔和机械朗读。

先用同一段20—30秒稿件比较少量候选声音与语速，自主选择最佳效果，再生成全片。

尽量按有完整语义的短段落合成，保持语境、重音和句间衔接。不要把每句话孤立合成后硬拼，导致音色与停顿不断重置。

按语义安排停顿，不机械逢标点就停相同时间。

句尾自然收束，转入新模块时留出正常停连；关键结果适度强调。

先按自然语速控制文字量，再调整镜头。不要为了塞满固定片段，持续使用明显加速的人声。

必要的微调应保持自然；某段过长时优先删减冗余文字或延长对应画面。

对“学脉、刘嘉程、DeepSeek、Flash、Pro、Python”和关键数值单独检查读法。角色名字、英文词和算法简称发音统一。

以配音试听和音画配合评价自然度。语音回转写适合检查错字、漏读与术语，但字符一致率不能替代对节奏和听感的检查。

语音素材与声音来源合法可用，不需要用户提供真人录音或参与配音制作。

十四、字幕与音画同步

字幕取消深色背景色块。

采用透明背景：
浅色画面配深墨色文字；
深色画面配浅色文字；
必要时使用细描边或轻微阴影提高对比。

不使用黑色或深色半透明矩形条，不用大色块占据底部。

设置稳定的字幕安全区，不覆盖输入框、题目答案、分页、操作按钮和重要结果。

每条字幕控制为一至两行，按自然语义分句，给足阅读时间。

字幕不是完整照搬一大段稿件压满画面，也不因追求短句而拆断专有名称。

制作顺序：

确定主线与镜头；
录制真实操作；
完成基本剪辑；
依据画面精修讲稿与配音；
对齐字幕；
再检查最终成片。

讲到语音时，应出现语音操作或结果；
讲到任务发布时，应出现发布动作；
讲到学生完成时，必须有学生完成画面；
讲到反馈时，要展示对应反馈结果。

参考当前产品与开发记录调整镜头，不依赖大量固定秒数等待来强行对齐。

十五、AI 协同过程：放在主体演示之后，清楚呈现真实开发

有效展示时长不少于120秒，建议约130秒。

这部分讲的是使用 Codex 开发学脉的过程，不是系统内部教学智能体的运行过程。

使用至少三条完整、真实的开发案例，优先复用已经核验过的证据：

课程对象与接口契约；
知识图谱改造与问题修复；
教师 AI 任务识别或专题证据修复。

每条展示：

原始需求或 Prompt；
AI 实现及遇到的实际问题；
关键代码变化；
测试与验证；
中文 Git 提交；
修改后的产品效果。

画面以真实交互记录、代码差异、测试终端和产品画面为主，配合精致的标题与局部高亮。

可以使用辅助画板组织证据，但不能把整段做成静态文字幻灯片。

原始记录的日期、角色、提交和结果保持准确。本轮新发生的工作按本轮事实记录。

长代码只突出关键变化；原始证据可追溯，画面展示则优先保证可读性。

演示完成后再进入简短总结与感谢，不把大量安装说明或其他内容放在开发片段后面打散结尾。
