## 一、任务定位与总体目标

继续升级现有 GitHub 仓库：

`https://github.com/Sunny1004-7/xuemai-ai-platform`

本轮不是重新开发项目，而是在现有第二轮版本的基础上，进一步提升系统的**技术创新性、算法深度、AI 教学能力、功能完整度、界面精致度、可视化水平以及整体获奖竞争力**。

项目仍然定位为：

**学脉 XueMai——师生双端 AI 个性化智慧教育平台。**

**现有系统已经形成完整的功能基础，但演示数据规模、知识图谱呈现、核心算法的创新深度、真实 AI 应用能力及教学可视化，仍然有显著的提升空间。**

请以高水平 AI 创新应用竞赛作品为标准，从产品、算法、视觉和工程四个层面进行系统性升级。

所有技术设计、代码开发、测试、界面调整和问题修复均由 Codex 自主完成。

首先审阅现有工程并确定修改顺序，然后直接修改真实代码、运行测试、检查截图、修复问题，并分阶段提交 GitHub。

## 四、DeepSeek 官方 API 调用策略调整

现有后端：

`backend/app/ai.py`

当前默认采用 Mock 模式。

本轮调整为：

**在配置有效 DeepSeek API Key 的正式交互环境中，直接使用真实 DeepSeek 官方 API。**

不需要继续因为担心 API 额度而长期默认使用 Mock。

用户已经提供 DeepSeek 官方 API Key。

可以在实际的教学功能中正常使用：

- AI 学习辅导。
- AI 生成习题。
- AI 备课。
- AI 主观题辅助评阅。
- AI 错因诊断。
- AI 教学策略规划。
- 多智能体教学协作。

### 4.1 使用原则

1. 正式产品运行时优先使用真实 DeepSeek。
2. 自动化单元测试与常规回归测试继续使用 Mock。
3. 真实 API 联调只做必要的少量验证。
4. 不开展大量重复调用、批量生成实验或高成本模型评测。
5. 尽量使用简短、具有代表性的测试输入。
6. 保留请求次数、Token 用量和实际调用状态记录。
7. 对重复教学内容可使用合理缓存，减少无意义消耗。
8. 对需要多次模型协作的流程，合理控制调用轮数。
9. API Key 只在后端使用，不得出现在前端或 GitHub。
10. API 错误需要有正常、清晰的用户反馈。

不再把历史的 3/5 次调用记录理解为平台永久只能再调用两次。历史用量记录继续真实保存，但正常产品使用和开发测试应采取不同的额度控制策略。

**真实产品可以正常调用 API，自动化测试不应大量消耗 API 额度。**

### 4.2 AI 状态展示

不需要在全平台顶部反复展示“本地演示模式”等技术状态。

与 AI 调用有关的加载、连接失败、模型响应状态，可以自然地展示在 AI 功能区。

在开发环境中保留必要的模式检查和调试入口。

不要将 Mock 内容冒充为 DeepSeek 的真实回答。

## 五、知识图谱：本轮最重要的前端专项改造

当前主要涉及：

- `frontend/src/pages/Graph.tsx`
- `frontend/src/graph-layout.ts`
- `frontend/src/styles/graph.css`

目前的知识图谱已经使用圆形节点、章节分组和自动布局。

但是，从当前截图看，多个先修连接线跨越不同章节，存在大量交叉与重叠。

节点内部文字较小，一些连线在节点附近密集聚合，整体观感混乱。

**本轮必须把知识图谱升级为兼具视觉美感、结构清晰度和实际交互能力的核心展示模块。**

### 5.1 重新设计图谱布局

不要继续依靠固定的三列章节网格和简单贝塞尔连线处理整个复杂知识网络。

请重新研究适合有向知识先修图的布局方案。

可以使用成熟的图布局技术，例如：

- ELK.js。
- Dagre。
- 分层有向图布局。
- 带章节约束的力导向布局。
- 边路由与交叉最小化算法。
- 自定义节点碰撞检测与局部布局优化。

最终技术由你根据实际效果自主决定。

必须重点解决：

1. 节点之间不能出现明显重叠。
2. 节点文字不能被其他节点或连接线遮挡。
3. 连线应尽量减少交叉。
4. 连线的起点和终点应对应正确节点边缘。
5. 箭头应清晰表达先修关系方向。
6. 不同章节应具有合理的空间组织。
7. 跨章节连接不能形成难以辨认的大量线团。
8. 节点密度与视口大小应协调。
9. 缩放后仍然能够识别主要结构。
10. 新增、删除和修改知识点后，布局能够稳定更新。

不要通过无限缩小节点和文字来强行塞下全部内容。

### 5.2 改为分层、渐进式图谱展示

我建议将图谱设计成三个层次。

**第一层：章节总览**

默认展示课程主要章节或知识主题，以少量具有设计感的章节节点构成清晰结构。

用户能够迅速看懂整个课程知识体系。

**第二层：章节知识网络**

点击章节后，展开对应章节中的具体知识点。

突出知识点内部关系以及与相邻章节的重要先修连接。

**第三层：知识点局部关系**

点击具体知识点后，突出：

- 当前知识点。
- 直接先修知识。
- 直接后续知识。
- 当前学习状态。
- 关联视频。
- 关联习题。
- AI 辅导。
- 交互实验。

其他无关连接弱化或隐藏。

需要保留“全图”查看能力，但不必在默认视图中同时突出全部节点和全部连接。

### 5.3 圆形节点视觉优化

继续采用圆形或圆环节点，但重新设计：

- 节点尺寸层级。
- 内部文字。
- 掌握状态环。
- 章节节点与知识节点区别。
- 当前选中节点。
- 鼠标悬停。
- 聚焦与展开动画。
- 先修关系高亮。
- 学习状态的颜色与形状编码。

尽量使圆形节点显得精致、轻盈、清楚。

不要使用大量重叠描边和过密连接制造视觉噪声。

图谱主色沿用学生端青瓷色或教师端茶褐色，并通过辅助颜色建立适当区分。

### 5.4 新增全屏知识图谱功能

**必须提供明确的“全屏查看”按钮。**

点击后进入独立的图谱全屏工作区。

全屏模式应支持：

- 最大化利用屏幕空间。
- 隐藏普通侧边导航。
- 隐藏不必要的页面标题与说明。
- 显示完整的图谱操作工具栏。
- 章节选择。
- 节点搜索。
- 缩放和平移。
- 适配视图。
- 选中知识点。
- 节点关系聚焦。
- 章节展开和收起。
- 图谱概览或小地图。
- 学生学习状态切换。
- 教师知识结构查看与编辑。
- 退出全屏并恢复普通页面。

建议支持 ESC 退出。

可使用浏览器 Fullscreen API，必要时提供兼容的全窗口模式。

全屏不应该只是将原来的 SVG 拉大，而应该重新利用空间调整布局、工具栏和详情面板。

进入和退出全屏时，应尽可能保持当前选中节点和视角。

### 5.5 图谱交互验收

必须用真实课程数据验证：

- 30 个以上知识点。
- 多章节先修关系。
- 复杂跨章节关联。
- 新增节点后的自动重排。
- 搜索定位。
- 聚焦先修链。
- 节点详情。
- 学习资源跳转。
- 教师知识编辑。
- 全屏进入与退出。
- 移动端查看。

建议增加布局几何检查和截图回归。

重点记录节点碰撞、文字遮挡、连线交叉及边界裁切情况。

本轮知识图谱应成为整个平台最有辨识度的交互可视化模块之一。

## 六、扩充演示数据，构建真实复杂的教学业务规模

当前演示数据库主要围绕一名学生展开。

从教师端学情截图可以直接看到“课程学生：1”。

这不适合展示真正的班级教学、学生差异与分层教学能力。

**本轮必须显著提高演示数据的规模、丰富程度和业务真实性。**

### 6.1 演示账号与班级数据

正式登录界面仍然只需要两个便捷入口：

- 一个学生端体验账号。
- 一个教师端体验账号。

但教师端必须能够管理一个具有正常人数和学习差异的教学班级。

建议：

- 建立约 24–30 名不同的合成学生。
- 保留一个主要体验学生，便于学生端完整操作。
- 其他学生作为教师端可管理的班级成员。
- 根据需要建立两个具有不同教学内容的班级。
- 保留现有多学生、多课程的数据模型。

**两个体验入口不等于数据库只能有两名用户。**

这些学生应当具有不同的学习状态、作答记录、知识困难、任务完成情况和复习表现。

### 6.2 构造多样化学习行为

演示学生不能只是改一下姓名，复制相同的数据。

应该构建具有真实教学逻辑的不同学习类型，例如：

- 基础概念较扎实的学生。
- 前置知识薄弱的学生。
- 理解概念但操作步骤容易出错的学生。
- 需要更多提示才能完成练习的学生。
- 练习正确率较高但知识迁移困难的学生。
- 近期学习进步明显的学生。
- 存在间隔复习需求的学生。
- 近期参与度下降的学生。
- 个别知识模块表现突出的学生。
- 多个知识模块均需关注的学生。

学习表现应由真实的数据模型和业务逻辑计算产生，而不是直接在前端写死一个分数。

### 6.3 扩充演示教学内容

建议提高以下内容的丰富程度：

**课程知识图谱**

保留已有知识结构，并进一步核对知识点与先修关系。

**智能题库**

覆盖更多知识点、题型和难度层级。

尽量为重要知识点提供多道不同层次的题目，而不是一个知识点只对应一道题。

**教师作业与测验**

构建多次不同时间发布的作业、阶段测验和针对性练习任务。

**视频教学**

增加有教学内容的可播放视频片段，关联字幕、时间戳、知识点与互动检查。

**AI 辅导**

准备不同错误场景和相关课程内容，使 AI 能够体现多种辅导策略。

**错题与复习**

构建不同时间、不同结果的订正与复测记录。

**教师分层教学**

建立多个不同教学问题群组及针对性的任务发布案例。

**课堂互动**

增加若干具有差异的课堂问答与学生参与记录。

### 6.4 数据生成质量要求

数据要尽可能接近真实教学环境中的逻辑关系。

例如：

- 学生必须先加入班级才能完成相应班级作业。
- 作答时间应符合任务发布时间。
- 教师端成绩应由学生作答记录计算。
- 错题状态应与实际作答结果一致。
- 学习计划应关联真正存在的课程资源。
- 知识掌握变化应有对应学习证据。
- 任务完成率与实际任务状态一致。
- 复习安排应符合真实记录的时间顺序。
- 不同学生应形成不同的知识掌握分布。

演示数据可以使用固定随机种子和规则生成，保证可重复构建。

应使用独立、幂等的演示数据扩充流程，避免破坏原有数据库和开发历史。

注意区分正式业务记录与自动构造的合成教学样本，不需要在每个前端页面重复显示“合成演示”等技术文字。

## 七、重点升级核心算法与方法，形成真正的技术竞争力

本轮除了 UI 和演示数据改进，**必须重点开展算法与教学方法升级**。

目前已经存在：

- Beta 加权学习证据模型。
- 时间衰减。
- 难度与提示权重。
- 同题重试折减。
- 先修知识图谱。
- 学习任务推荐。
- SM-2 类间隔复习。
- 结构化辅导动作。

这些是可以继续深化的技术基础。

本轮目标是让它们形成更加系统、具有明确方法定义和实际教学效果链路的核心技术体系。

### 7.1 核心方法一：知识状态动态估计

建议研究并实现：

**K-TRACE：基于知识先修约束与时序多维学习证据融合的动态知识状态估计方法**

名称可以由你进一步优化。

核心思路：

综合学生在不同时间、不同题目和不同学习活动中的表现，对知识点状态进行动态估计。

可考虑融合：

- 题目难度。
- 作答正确性。
- 提示使用程度。
- 首次作答与重复作答。
- 学习时间。
- 复习间隔。
- 分步作答结果。
- 知识先修关系。
- 有效证据数量。
- 状态估计的不确定性。

需要特别完善当前 Beta 证据模型的含义与展示方式。

例如，未经学习证据支持的先验均值不能直接被理解为学生实际掌握了相应比例的知识。

应明确区分：

- 尚无充分证据。
- 当前估计状态。
- 有效证据量。
- 状态变化。
- 估计的不确定性。

对于模型中的先修关系，应明确其作用方式，避免把前置知识不足简单等同于后续知识一定不会。

要求提供真实数学定义、核心计算逻辑、参数来源和算法测试。

### 7.2 核心方法二：个性化学习路径规划

建议研究并实现：

**PATH-G：基于知识图谱与多目标约束优化的个性化学习路径规划方法**

核心目标：

根据学生当前知识状态、课程要求和先修结构，生成合理的学习活动序列。

规划时考虑：

- 当前目标知识点。
- 前置知识。
- 学生学习困难。
- 教师布置的任务。
- 学习材料可用性。
- 习题难度。
- 预计学习成本。
- 复习到期情况。
- 当前知识状态不确定性。

推荐结果不应只是按照一个优先级分数排序。

要能够组织具有前后关系的学习任务。

例如：

先修知识补学 → 视频片段 → 交互实验 → 针对性练习 → 理解检查 → 间隔复测。

需要形成可执行的路径规划机制，提供推荐理由，并能够在学习结果变化后重新规划。

可采用成熟的 DAG 约束规划、有限搜索或多目标排序算法，不必为了创新而引入昂贵计算。

### 7.3 核心方法三：多智能体协作教学

建议重点建设：

**DIA-GUIDE：基于多智能体协作的学习诊断—教学干预—理解校验闭环方法**

这是本轮值得重点投入的 AI 创新能力。

建议采用职责明确的教学智能体协作架构。

例如：

**诊断智能体 Diagnostic Agent**

分析当前题目、学生回答、错误步骤和知识状态，识别可能的学习困难。

**教学策略智能体 Pedagogical Agent**

结合诊断结果、课程内容和教学目标，选择适当辅导策略。

例如概念解释、苏格拉底式追问、反例辨析、可视化讲解或变式训练。

**校验智能体 Verification Agent**

检查生成内容与课程材料、题目条件和确定性知识是否一致，并组织适当的理解检查。

注意，多智能体协作不能只是三个不同名称的 Prompt。

必须实现：

- 明确的智能体输入和输出。
- 结构化状态与消息。
- 不同的职责与任务。
- 真实的协作流程。
- 智能体之间的信息传递。
- 可调用的教学工具。
- 输出内容校验。
- 教学动作执行。
- 学生反馈。
- 下一轮教学调整。

AI 生成的教学动作应当真实连接平台已有功能。

例如：

诊断学生错误 → 选择知识点解释 → 打开交互实验 → 引导学生操作 → 提出理解检查 → 根据结果推荐下一道题。

需要让评委能够看到 AI 智能体如何真正改变教学方式。

### 7.4 核心方法四：分层教学与干预匹配

建议研究并实现：

**CLASS-LOOP：基于多粒度错因聚类与教学反馈的自适应分层教学方法**

核心目标是让教师能够依据班级学习差异制定不同教学任务。

方法应综合：

- 学生知识状态。
- 典型错因。
- 前置知识薄弱情况。
- 学习进度。
- 作业结果。
- 复习需求。
- 学习任务完成情况。

根据真实学习证据形成不同的教学关注群组。

教师可以针对不同群组发布差异化任务。

学生完成任务后，系统更新相应状态，并让教师观察变化。

群组应随着学习证据变化而动态调整，而不是为学生永久贴上固定能力标签。

### 7.5 算法与方法的实际交付要求

上述名称是建议方向，可以根据实际技术实现进一步优化。

最终至少形成**三个真正完成并经过验证的核心算法或方法**。

每个方法必须具备：

1. 正式名称。
2. 简称及中文全称。
3. 解决的问题。
4. 输入与输出。
5. 核心技术思想。
6. 数学或逻辑定义。
7. 算法流程。
8. 对应源码位置。
9. 实际应用场景。
10. 自动化测试。
11. 与现有简单方法的对比。
12. 实际限制和适用条件。

不能只给现有启发式规则起一个高级名字。

也不能在未实现真实技术机制的情况下，把普通 API 调用写成重大算法创新。

创新点应落在具体的模型融合、任务规划、教学协作机制或反馈流程上。

### 7.6 算法验证与对比

为核心方法建立可复现的实验用例。

可以比较：

- 固定加减分与多维证据估计。
- 静态排序推荐与先修约束路径规划。
- 普通单轮 AI 回答与结构化教学协作。
- 简单按成绩分组与基于错因的动态分层教学。

必要时进行消融测试，检查去掉某个模块后系统行为如何变化。

评价重点包括：

- 计算逻辑正确性。
- 不同输入下的稳定性。
- 推荐路径有效性。
- 先修约束满足情况。
- 教学动作执行成功情况。
- 不同错因是否产生合理差异化策略。
- 算法效率和资源开销。

实验应以程序化生成的数据和实际运行结果为基础。

不要编造算法准确率、学习效果提升比例或其他未经验证的性能结果。

### 7.7 核心算法文档

建立独立工程文档，例如：

`docs/ALGORITHMS_V3.md`

清晰整理上述核心算法与方法。

内容包括数学定义、流程图、实现架构、真实测试结果及对应代码位置。

同步更新必要的工程说明。

技术文档 PDF 和演示视频的专项修改要求由本任务书末尾的预留章节另行规定。

目前学生首页主要展示任务、课程和近期学习记录。

例如：

**学习进展趋势**

展示最近一段时间的有效学习表现或任务完成变化。

展示不同知识点下学生学习状态的分布情况，而不是只有一个班级平均值。

**错因分布与关联**

展示概念问题、操作步骤问题、先修知识问题等不同类型的错误。

**学习进展趋势**

展示一段时间内的练习表现、任务完成和知识状态变化。

**分层教学群组**

以清晰的分组卡片、条形图或矩阵展示不同教学关注群组，以及每组需要的学习任务。

**教学干预反馈**

教师发布针对性任务后，展示完成情况、后续测验表现和对应知识证据变化。

### 8.3 可视化设计要求

可使用 ECharts、D3 或其他成熟方案。

必须保证：

- 数据真实来源于后端。
- 图表颜色语义清晰。
- 数值与文字一致。
- 教师和学生端的相同指标采用统一定义。
- 支持悬停详情和必要的点击下钻。
- 长标签能够正确显示。
- 无数据和少数据时正常处理。
- 不因丰富演示数据而出现性能问题。
- 桌面和移动端均具有合理布局。

优先选择适合表达实际信息的图形，不要为了视觉冲击力强行使用复杂 3D 图表。
